# RIONIX AI共同制作の実証結果 — v0.8

検証日: 2026-10-28（日本時間）。本レポートの対象はこのWorkセッションとこのアプリ。一般的な全ChatGPT環境の保証ではない。

## 結論と3段階判定

1. 操作できる: 部分的に実証済み。公開ページを開き、編集設定をUIで取得し、JSONを書き換え、確認ダイアログを経て反映し、15秒のプレビュー完了を確認した。
2. 映像を確認できる: 実証済みの範囲はブラウザーの静止画、および出力MP4の時刻指定フレーム抽出・目視と全フレームの機械検査。連続動画を音楽とともに人間同様に鑑賞し全演出を評価したわけではない。
3. 評価して修正できる: テスト素材で限定的に実証。初稿出力のCHORUS登場が10秒なのにテスト音の変化は7秒であることを確認し、3/4/8秒配分・寄り引き・0.4秒フェードに変更して修正版を生成。修正版でCHORUSが7秒に到達することを出力から確認。6.8秒のクロスフェードでは素材内の英字が二重に見えるため、この素材にはカット切替を推奨できる。実楽曲の美的な「盛り上がり」の評価は未実証。

## 1. 現行アプリと実行環境

GitHub Pagesの静的HTML/JS。スマホではCanvas＋Web Audio＋MediaRecorderでH.264/AACを録画。IndexedDBはそのブラウザー内。今回のクラウドブラウザーは現行MIME候補を拒否し、対応状況欄に「H.264＋AACのMP4録画に対応していません」と表示。素材読み込み後もMP4ボタンは無効。対応しない環境で録画成功を装う変更はしていない。

公式資料もWorkのクラウドブラウザーはスマホ/PCのローカルブラウザーとは別のコンピューターと説明している。https://learn.chatgpt.com/docs/browser
今回もスマホ内の素材・保存内容は直接取得していない。

## 3. 実施した制作サイクル

ユーザー指定の実素材は今回まだない。無関係な個人素材は使用せず、3枚の図形と英字の画像、20秒の合成音を作成した。素材/設定/動画は成果物ZIPに同梱。

- 初稿: 5/5/5秒、動きなし、カット、音声開始2秒。
- 初稿のMP4からフレームを抽出して目視。CHORUSは10秒から。
- 修正判断: テスト音の高さが変わる動画7秒へCHORUSを前倒し。
- 修正版: 3/4/8秒、寄り/引き/寄り、0.4秒フェード、字幕を変更。
- 修正版MP4も抽出フレームで目視。CHORUSへのフェードは6.6秒から、完了7秒。終盤の寄りも画像比較で確認。
- ユーザーによる両動画の再生・評価はこれから。

両動画は1280×720、30fps、15.000秒、H.264＋AAC、450フレーム。ffprobeでコーデック/時間を確認し、FFmpegで全450フレームをデコード。画面隅の色からCHORUSの完全表示は初稿10.0秒、修正版7.0秒と測定した。AACをPCMへ戻した周波数解析では6.5秒の窓で440Hz、7.0秒の窓で880Hz。合成テスト音での時刻整合の確認であり、実楽曲の知覚的同期や音質保証ではない。

目視は3秒間隔のシートと修正版0/2.9/3.1/6.6/6.8/7/10/14.9秒の8枚。全450フレームをモデルが一枚ずつ見たわけではない。数値検査も全種類の映像不良を検出する保証ではない。

## 4. 今回の実装と安全境界

- src/edit-plan.js: バージョン付き設定JSON、素材名/サイズ照合、秒数・動き・字幕・開始位置・出力設定の制約。準備中は元の編集を変更しない。
- 本番UI: 設定取得、JSON入力、変更一覧付き確認ダイアログ、反映。ファイル本体送信・自動録画・自動保存はしない。
- tools/render-plan.mjs: Workまたはローカルで実行。ブラウザーと同じdrawFrame/字幕コードを使用し、ネイティブCanvasとFFmpegでMP4化。素材は指定ディレクトリ内のみ、外部URLやコードを実行しない。既存出力を上書きしない。5分上限、80MiB出力上限（CLIは終了時検査）。
- tests/ai-proof.html: 本番と同じUI/モジュールを使うテスト専用ページ。ボタンが合成Fileを作り、実際の画像/音声onchange処理へ渡す。OSファイル選択・ユーザーファイル転送の代わりには数えない。
- APIキー、公開書込API、サーバー認証、外部アカウント契約を追加していない。公開サイトの利用自体は認証不要。GitHub更新は既存コネクター権限で実行。
- JSONには素材名が含まれる。渡す際は名前にも個人情報がないか確認する。名前＋サイズは誤素材防止であり暗号学的照合ではない。
- 確認ダイアログは操作前のチェックポイントであり、AIが絶対に承認できない権限制御ではない。今回のテスト素材の反映はユーザー依頼の範囲内でWorkが承認した。将来の有料処理/外部公開は別の権限境界が必要。

## 5. テスト結果と未検証

24件のNodeテストが通過。JSON往復・元データ不変・不正値/素材不一致/パス逸脱拒否を追加。ビルドと構文チェック通過。GitHub Pagesでv0.8表示、テストページの素材読込、取得→修正→確認→反映、15秒プレビュー完了を確認。

未検証: v0.8のAndroid実機回帰、実素材のスマホとWork間の往復、CLIでの日本語フォント品質/1080p/60秒、今回のブラウザーによるMP4出力、実楽曲の感性評価。CLIはブラウザーと同じ描画関数でも画像補間・フォント・エンコーダーが異なるためピクセル一致は保証しない。英字デモでもフォント差が見える。

## 6. 推奨構成と残る作業

推奨はC: スマホUIとWorkがバージョン付き編集計画を共有し、描画ロジックを共通化。出力を時刻付きフレーム・音声測定・差分へ変換してWorkへ戻す。現時点では素材と設定の受け渡しは手動、スマホへの反映もユーザーの確認が必要。

次に必要なのは、素材＋設定を一括で受け渡すプロジェクトパッケージ、SHA-256の素材ID、変更差分/取り消し、CJKフォント固定、同一素材での端末間比較。さらに実楽曲のサビ位置をユーザーと合意し、その区間に対する変更と出力レビューを実証する。

常時稼働のクラウドレンダリング/API/MCPは将来案。認証、素材アクセスの期限・権限、費用上限、公開前承認が必要で、今回は実装していない。GitHub PagesだけでネイティブFFmpegを稼働させることはできない。Work実行環境も恒久サーバーではなく、ツール/依存関係/容量/時間の利用可否はセッション依存。追加契約なしで今回の小規模実証は完了したが、将来の処理量や無料継続を保証しない。

最終成功条件は部分達成。テスト素材で「変更→生成→出力確認→再変更→再生成」は成立。スマホから素材を渡すだけで実楽曲MVを自律的に完成する体験は未完成で、ユーザー素材での共同制作が次の検証対象。
